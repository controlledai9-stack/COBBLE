# Local fresh-session recovery evidence

Date: 5 November 2026. Scope: the trusted deterministic simulator baseline. Full R2/R5 recovery and cancellation remain incomplete.

`POST /api/response/agents/{id}/recover-fresh` accepts the existing revisioned resume fields: source run, incident, exact restriction IDs, reason and principal revision. It requires operator authentication and an idempotency key. Recovery is restricted to registered local simulator slots. A stopped principal cannot use this route. An in-flight, prepared, dispatched or unknown effect must be reconciled first, including operations created by older code whose principal is recovered through session lineage.

Preparation atomically records a recovery intent and advances the principal context epoch while setting `state=recovering`. It releases no holds yet. Every new session records its agent-to-context epochs; historical sessions belong to epoch one. Old runners, including their memories/inboxes/pending decisions, are fenced at actual tool admission and event boundaries. Monitor mode cannot bypass a stale context, stopped/recovering principal, stale policy or integrity failure.

The service creates a new run using the server-owned deterministic normal-collaboration configuration. It accepts no caller task, model, adapter, environment, broker, workspace or checkpoint files. Before any new work, the engine invokes an internal completion callback that verifies the designated run/principal/epoch, empty agent memories and pending tasks, empty broker delivery history, no prior runner events, and no planted/unread input state. Only the normal fresh environment factory is supported; supplying a mutable environment is refused.

Completion rechecks principal revision, policy epoch, no pending effects and the active named restrictions. In one transaction it releases only those restrictions, clears the recovering principal's old in-memory context label, restores active state, records an executor-owned local initialization receipt and adds a durable operator notification. Other incident restrictions, old run/resource labels, message holds, quarantined artifacts, approvals and external effects are not released or undone. Old action approvals also fail principal-revision/context applicability. No contaminated user task or prior instruction is resumed.

`GET /api/response/recoveries/{id}` returns the durable state and fresh run ID. Repeat requests with the same idempotency key observe that recovery; they do not create another fresh run. Interrupted preparation leaves the principal held. Recovery completion means the local new-context initialization was verified, not that all later work succeeded. A runner or policy race remains held rather than inventing cancellation evidence.

Tests in `test_response_recovery.py` exercise both enforce and monitor profiles: old poisoned memory stays physically present but cannot produce later effects; named clean-context restrictions release while an unrelated egress hold remains; simple resume cannot release a clean-context hold; unknown effects prevent epoch reset; and a supplied environment is refused with the principal still recovering. The local receipt deliberately reports external process/credential cancellation as unsupported.

Remaining gates include broader trusted checkpoint types, hosted/LLM-provider context recovery, process/queue/credential cancellation, reviewed declassification, resource/output cleanup policy, restart/clock/load qualification, UI and production identity. The new local path does not satisfy those broader requirements.

Observed verification: the Docker-enabled full backend run passed **708 tests in 202.57 seconds**, no skips. The final control-integrity guard was then covered by the current recovery/control/runtime/message suites: **53 passed**, including ten recovery cases across enforce and monitor profiles. One existing FastAPI/httpx deprecation warning remains. No frontend contract changed in this step.
